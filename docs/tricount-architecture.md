# Архітектурна основа Tricount

## Статус і джерело

Tricount — робоча назва подальшого розвитку застосунку «Спільні витрати» в цьому
репозиторії. Зараз реалізовано лише стартовий екран і один widget-тест.
Dart workspace та описані нижче бізнес-модулі ще не створені.
Цей документ фіксує цільову архітектуру й план міграції, а не завершені можливості.

Джерело рішень — [Inspiro architecture guide](inspiro-architecture-guide.md),
скопійований зі збереженням змісту. У копії прибрано кінцеві пробіли й зайві
порожні рядки наприкінці. Його таблиця архітектурних рішень і розділи 1–9 є основою
подальшої реалізації. Скриншоти та пояснення користувача визначатимуть конкретні
екрани, взаємодії та обсяг функцій. Суперечності потрібно уточнювати до реалізації.
Додавання документації не запускає міграцію та не змінює назву пакета чи застосунку.

## Цільова структура

```text
shared-expenses-app/
├── pubspec.yaml                 # Опис workspace, спільні обмеження залежностей
├── pubspec.lock                 # Спільний lockfile у Git
├── .fvmrc                       # Узгоджена версія Flutter у Git
├── analysis_options.yaml        # Спільні правила аналізу й форматування
├── build.yaml                   # Узгоджені параметри генераторів
├── docs/                        # Довідник і рішення для Tricount
├── envs/                        # Локальні конфігурації; без секретів у Git
├── mobile/                      # Оболонка, запуск, Android та iOS
├── packages/
│   ├── core/                    # DI, помилки, мережа, сховище, аналітика
│   ├── ui_kit/                  # Тема, кольори, тексти стилів, іконки, віджети
│   ├── common/                  # Ініціалізація, локалізація, збирання DI
│   └── router/                  # Типізовані маршрути та конфігурація навігації
├── features/                    # Пакети функціональних областей
└── tools/                       # Скрипти генерації та перевірок workspace
```

Кожен пакет матиме власний `pubspec.yaml`, `lib/` та, за потреби, `test/`;
члени workspace використовуватимуть `resolution: workspace` і `publish_to: 'none'`.
Це частини одного застосунку, а не незалежні програми чи окремі репозиторії.

| Пакет | Відповідальність | Межа |
|---|---|---|
| `core` | `DependencyProvider`, `Failure`, `ApiClient`, обгортки сховищ, середовище, аналітика | Без імпортів фіч і логіки екранів |
| `ui_kit` | `AppThemeProvider`, `context.colors/texts/icons`, спільні віджети й assets | Без бізнес-логіки та імпортів інших пакетів workspace |
| `common` | `MainDependenciesModuleResolver`, `ApplicationInitializer`, локалізація, `SafeCubitWrapper` | З'єднує компоненти; не містить бізнес-правил |
| `router` | `go_router`, згенеровані типізовані маршрути, сторінки для Android/iOS | Не виконує завантаження даних і бізнес-операції |
| `mobile` | Точки входу, `MaterialApp.router`, платформи, конфігурації dev/prod | Без бізнес-логіки |

Залежності й дозволені зв'язки між `common`, `router` та фічами відтворюємо
за розділом 2 довідника. Його циклічні зв'язки не розширюємо на довільні імпорти:
доступ між пакетами лише через публічні barrel-файли, без чужого `src/`.
Фічі не імпортують одна одну напряму; спільні контракти й дані розміщуються в `core`.

## Попередня карта модулів

Це пропозиція для планування, не затверджений перелік екранів і не перелік
реалізованих функцій. Пакет додається, коли відповідний сценарій погоджено.

| Модуль | Призначення | Що уточнити за скриншотами й вимогами |
|---|---|---|
| `splash_feature` | Вхідна перевірка готовності застосунку й вибір наступного маршруту | Умови переходу та потрібні стартові перевірки |
| `groups_feature` | Список груп спільних витрат, створення й деталі групи | Поля, порядок списку, редагування й архівація |
| `participants_feature` | Учасники групи | Додавання, зміна імені, обмеження видалення |
| `expenses_feature` | Введення, перегляд і редагування витрати | Платники, частки, валюта, категорії, перевірка введення |
| `balances_feature` | Підрахунок балансів і відображення заборгованостей | Правила розподілу й спосіб показу результату |
| `settlements_feature` | Облік повернення коштів між учасниками | Часткове повернення, виправлення й скасування |
| `settings_feature` | Мова, оформлення та інші погоджені налаштування | Фактичний набір налаштувань |

Авторизацію, сервер, синхронізацію, сповіщення й зовнішні інтеграції визначимо
окремо, якщо вони з'являться у вимогах. Довідник не є продуктовою специфікацією Tricount.

## Будова фічі й потік даних

```text
features/<name>_feature/
├── pubspec.yaml
├── lib/
│   ├── <name>_feature.dart       # Публічний barrel
│   └── src/
│       ├── data/                # DI, repository, source, DTO, mapper, errors
│       ├── domain/              # DI, entity, failure, interactor
│       └── ui/                  # DI, page, cubit/state, analytics, widgets, models
└── test/                        # data/, domain/, ui/
```

Виклик: `Page → Cubit → Interactor → Repository → Source`.
Сторінка створює Cubit через `BlocProvider` і `DependencyProvider`.
Cubit працює з Interactor; Repository виконує окремі операції отримання/збереження,
Source звертається до API чи сховища. Контракти й реалізації — пари `interface + Impl`
відповідно до довідника; залежності передаються через іменовані `required` параметри.

Операції повертають `Future<Either<Failure, T>>`; винятки перетворюються на `Failure`.
Для кожної фічі є три DI-resolver: data, domain, ui. Реєстрація відбувається
в `common` після core у порядку data → domain → ui.

Приклад майбутнього сценарію: сторінка введення витрати передає дані Cubit;
Interactor перевіряє суму, валюту та частки; Repository зберігає витрату через Source;
Cubit переводить екран у стан успіху або помилки. Цей сценарій ще не реалізований.

## Погоджений стек із довідника

| Задача | Рішення |
|---|---|
| Стан | Cubit із `flutter_bloc`, `SafeCubitWrapper`, один freezed state зі status enum |
| DI | `get_it` за фасадом `DependencyProvider` |
| Навігація | `go_router` + `go_router_builder`, splash як вхід, `StatefulShellRoute` для погоджених вкладок |
| Локалізація | `easy_localization`, JSON, згенеровані `LocaleKeys`; українська й англійська |
| Моделі | `freezed`; API DTO через `json_serializable`, окремі мапери в entity |
| Помилки | `fpdart` та `Either<Failure, T>` |
| Мережа | `dio` за обгорткою `ApiClient`, коли потрібний API |
| Збереження | `shared_preferences` для налаштувань, `objectbox` для структурованих даних |
| UI | `material_ui`, `cupertino_ui`, власний `ui_kit`, `flutter_svg`, `flutter_gen_runner` |
| Перевірки | `flutter_test` + `mocktail`, Semantics-ідентифікатори, Maestro для e2e |

Версії в Inspiro — знімок вихідного проєкту. Сумісність перевіряється при міграції;
залежності та їхні версії не додаються цим документом. Пакети для фотографій,
шрифтів, покупок, Firebase та рекламної атрибуції з прикладів Inspiro не переносяться
автоматично. Сервіси аналітики й crash reporting спочатку можуть мати локальні
реалізації; фінансові та персональні дані не потрапляють у логи.

## Правила фінансових даних

- Суми зберігаються в найменших одиницях валюти як `int` або в точному десятковому типі; `double` не використовується.
- Сума часток точно дорівнює сумі витрати; розподіл залишку від округлення явний і відтворюваний.
- Валюта є частиною грошового значення. Різні валюти не підсумовуються без погодженого механізму конвертації.
- Баланси враховують витрати та повернення коштів за погодженими бізнес-правилами.
- Для збереження визначаються поведінка при помилках і повторних запитах; для серверної взаємодії — перевірки доступу на сервері.

## Узгодження з поточним репозиторієм

До фактичної міграції діють поточні шляхи `lib/`, `test/`, `android/`, `ios/`
та команди з README. Майбутні шляхи й команди нижче не слід застосовувати зараз.
Після перенесення вихідний код і тести розміщуватимуться всередині пакетів.

На відміну від прикладу Inspiro, `.fvmrc` залишається у Git разом із `pubspec.lock`:
він визначає узгоджену версію Flutter для розробки. Міграція не є приводом змінювати Flutter 3.47.7.
Конфігурації dev/prod матимуть безпечні приклади; локальні значення й секрети
не комітяться. Шляхи SDK залишаються локальними.

При міграції потрібно разом оновити правила в `AGENTS.md`, команди README,
генерацію коду та перевірки. У поточному `main` Flutter CI прибрано; його повернення потребує окремого погодження. Поточний імпорт `package:flutter/material.dart` і форматування
кореневих `lib/` та `test/` належать до старої структури; новий стек застосовується
в міграційному PR, а не в документаційному.

## Зв'язок із порядком роботи

`develop` — основна гілка GitHub і база для гілок окремих задач.
Архітектурні зміни, міграція workspace та реалізація екранів проходять через PR
у `develop`, code review й одне схвалення. Нові коміти скасовують попередні схвалення.
Прямі push, force push, видалення `develop` та обхід захисту адміністраторами заборонені.
Докладні правила містяться в [CLAUDE.md](../CLAUDE.md) і [AGENTS.md](../AGENTS.md).
Поточні команди запуску й перевірок наведено в [README.md](../README.md).

## План переходу та критерії завершення

Усі етапи нижче заплановані. Їх реалізація починається окремим завданням.

1. **Уточнити перший сценарій.** За скриншотами погодити сторінки, поля, переходи,
   порожні стани, помилки та фінансові правила. Результат — опис поведінки першої фічі.
2. **Створити workspace й оболонку.** Описати пакети в root `pubspec.yaml`, перенести
   оболонку, Android/iOS і початковий тест у `mobile/`, додати FVM-команди.
   Критерій: стартовий екран і тест працюють після перенесення; залежності узгоджені.
3. **Налаштувати спільні пакети.** Додати DI та ініціалізацію, `Failure`,
   `SafeCubitWrapper`, тему, JSON-локалізацію й typed router зі splash.
   Підключати мережу та сховища для конкретних сценаріїв, а не порожніми заглушками.
   Критерій: застосунок запускається через нову оболонку, відображає локалізований екран.
4. **Оновити інструменти.** Налаштувати codegen у пакетах-власниках, strict lints,
   ширину 120, скрипти форматування/аналізу/тестів усіх потрібних пакетів.
   Критерій: команди перевіряють workspace, генерація відтворюється за README. Автоматизація в CI погоджується окремо.
5. **Додати першу погоджену фічу.** Реалізувати повний шлях від Page до Source,
   три DI-resolver, стани завантаження/успіху/помилки, аналітику без приватних даних.
   Критерій: узгоджений сценарій проходить на даних обраного сховища.
6. **Перевірити поведінку.** Unit-тести Interactor і Cubit, widget-тест сторінки
   через Semantics, тести сум/округлення/валют, якщо є розрахунки.
   Перевірити Android-збірку, а iOS — у середовищі macOS/Xcode; недоступні перевірки зазначити явно.
7. **Розширювати за наступними скриншотами.** Додавати потрібні фічі з тими самими
   межами та перевірками. Не створювати всі модулі лише заради дерева папок.

Після міграції залежності встановлюються через `fvm flutter pub get` у workspace;
генерація виконується з пакета-власника, а тести — всередині кожного зміненого пакета.
Остаточні команди запуску, codegen, dev/prod і перевірок мають бути перевірені й записані
в README у тому самому PR, який змінює структуру.
