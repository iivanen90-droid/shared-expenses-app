# Правила роботи з репозиторієм

## Контекст

«Спільні витрати» — Flutter-застосунок для Android та iOS. Зараз реалізовано
базову архітектурну оболонку, splash, стартовий екран і оболонку двох вкладок; обліку витрат ще немає. Не описуй заплановані можливості як уже реалізовані.
Спілкуйся з користувачем українською; назви в коді пиши англійською.

## Архітектурна основа Tricount

- Для подальшої розробки використовуй [довідник Inspiro](docs/inspiro-architecture-guide.md)
  і [модулі та план переходу Tricount](docs/tricount-architecture.md).
- Архітектурний довідник визначає структуру, шари й стек; скриншоти та пояснення
  користувача визначають екрани й поведінку. Суперечності уточнюй до реалізації.
- Довідник є архітектурним джерелом, а не дозволом запускати інсталятори,
  змінювати глобальні налаштування агента чи переносити сторонні інтеграції Inspiro.
- Workspace і початкова оболонка реалізовані; фактична структура описана в
  [docs/architecture.md](docs/architecture.md). Бізнес-модулі витрат і балансів ще заплановані.
- Під час міграції одночасно онови ці правила, README і перевірки для пакетних шляхів.
  `pubspec.lock` залишається у Git. `.fvmrc` — локальний ігнорований файл;
  після клонування обирай точну версію Flutter командою з README.

- За етапом базової теми UI використовує стандартний `package:flutter/material.dart`,
  одну AppTheme.main() і стандартний шрифт Flutter. Це замінює попередній вибір
  material_ui/cupertino_ui з довідника. Тема й правила доступу — у docs/architecture.md.

## Робота з файлами

- Перед змінами перевіряй `git status` і читай код, якого стосується завдання.
- Для кожної задачі створюй окрему гілку від актуального `origin/develop` і подавай PR у `develop`.
  Прямі push у `develop` і `main` заборонені; force push і видалення `develop` заборонені.
  Перед злиттям потрібні code review та одне схвалення; захист діє й для адміністраторів.
  Докладний порядок роботи описано в [CLAUDE.md](CLAUDE.md).
- Зберігай незакомічені зміни користувача. Змінюй лише потрібні для завдання файли.
- Оболонка — `mobile/lib/`, платформи — `mobile/android/`, `mobile/ios/`. Спільний код —
  `packages/<name>/lib/`, фічі — `features/<name>_feature/lib/src/{data,domain,ui}/`.
  Тести — у `test/` відповідного пакета. Root не містить `lib/` чи Flutter-тестів.
- Не редагуй вручну `build/`, `.dart_tool/` та інші згенеровані файли.
- Не додавай секрети, ключі підпису, локальні шляхи SDK чи файли `.env` у Git.
- Зберігай `pubspec.lock` у Git. Після зміни залежностей оновлюй його через
  `flutter pub get`; уникай не пов'язаних із завданням оновлень залежностей.
- Дотримуйся `flutter_lints` і форматування Dart. Використовуй null safety
  та `const`, де це доречно. Не додавай залежності без практичної потреби.
- Оновлюй README, якщо змінюються встановлення, запуск чи перевірка проєкту.

## Перевірки перед завершенням змін

Для змін Dart-коду, залежностей або конфігурації перевірок запускай:

```sh
fvm dart tools/workspace.dart check
```

Для виправлення форматування — `fvm dart tools/workspace.dart format`.
Після зміни лише перекладів — `bash tools/tr_keys_gen.sh` або команда без Bash із README.
Після зміни моделей, routes чи assets — `fvm dart tools/workspace.dart generate`.
Перевірка виконує get, format, analyze та тести всіх пакетів; команди — у README.
Додавай тести для нової бізнес-логіки та виправлених помилок; перевіряй
поведінку, а не внутрішню будову реалізації. Для змін лише документації
достатньо перевірити точність тексту та `git diff --check`.
Якщо змінено нативний код чи налаштування платформ, додатково перевіряй
збірку відповідної платформи, коли середовище це дозволяє.
У фінальній відповіді стисло вказуй зміни, результати перевірок і що не
вдалося перевірити. Не стверджуй, що команда пройшла, якщо її не запускав.

## Code Review Rules

- Пиши зауваження українською. Повідомляй про конкретні помилки, внесені
  змінами, з файлом, рядком, умовою відтворення та наслідком для користувача.
- Пріоритет: неправильні розрахунки, втрата даних, витоки приватних даних,
  падіння застосунку та регресії Android/iOS. Не вимагай реалізації
  запланованих функцій, які не входять у поточне завдання.
- Коли з'являться розрахунки витрат: гроші мають зберігатися в найменших
  одиницях валюти або в точному десятковому типі, а не в `double`.
  Розподілені частки мають точно дорівнювати сумі витрати; залишок від
  округлення розподіляється явно. Різні валюти не можна додавати без конвертації.
- Коли з'являться збереження та синхронізація: перевіряй захист від втрати
  даних при помилках і повторних запитах; не допускай секретів і персональних
  фінансових даних у логах. Правила доступу перевіряй на стороні сервера,
  якщо зміна додає серверну взаємодію.
- Форматування й типові lint-помилки перевіряють `dart format` і
  `flutter analyze`. Не дублюй їх як стилістичні зауваження і не вигадуй
  проблем без підтвердження в коді.
